# クラウドセーブ（ローカルセーブとの同期・引き継ぎ）

Issue #187 の実装。ログインしたユーザーのセーブを Supabase に保存し、別の端末で引き継げるようにする。ログインしなくても、通信できなくても、ゲームはこれまでどおり遊べて、ローカルへの保存も続く。Firebase の `user-sync`（`POST /quest/api/v1/user-sync`）は削除した。

> **信頼境界: クラウドセーブは自己申告のデータである。** クライアントが好きな内容を書ける。`completedObjectives` や `xp` を、ランキング、リーダーボード、チームスコアの加点元にしてはならない。ビュー、関数、集計、送信処理も作らない。将来、信頼できるスコアが必要になったら、サーバー側で検証する別の経路（Edge Function でイベントを検証して記録するなど）を作る。`public.cloud_saves` のテーブルコメントにも同じことを書いてある。

## 全体像

```
レンダラー (JS)                          Rust (src-tauri)                       Supabase
 同期エンジン ── cloud_save_fetch ───▶  cloud_save/   ── GET /rest/v1/cloud_saves ──▶ RLS: 本人の行だけ
 (common/cloudSave)  cloud_save_upload ─▶  (アクセストークンは auth のセッション) ── POST /rest/v1/rpc/upsert_cloud_save
       ▲                                       ▲
       └──── auth://status-changed ────────────┘  (秘密情報なし。account = ユーザー ID のハッシュ)
```

- ネットワーク通信は Rust 側だけが行う。認証（#186）と同じく、レンダラーにトークンもユーザー ID も渡さない。CSP の `connect-src` も変えていない。
- レンダラーはアカウントを、認証状態の `account`（ユーザー ID の SHA-256 の先頭 32 文字）で見分ける。2 つのコマンドは、呼び出し側が想定するアカウントを必ず受け取り、現在ログイン中のアカウントと違うときは `account_changed` で失敗する（別アカウントのセーブに触らない保険）。
- コマンド（`build.rs`、`capabilities/platform.json`、`permissions/autogenerated/` に登録）:
  - `cloud_save_fetch(expectedAccount)`: 自分のセーブ（`{ account, revision, updatedAt, schemaVersion, data }`）または `null`。
  - `cloud_save_upload(expectedAccount, data, schemaVersion)`: 書き込み。サーバーが採番した `{ account, revision, updatedAt }` を返す。
  - エラーは文字列のコードだけ: `signed_out`、`account_changed`、`offline`、`server`、`unauthorized`、`rejected`、`too_large`。URL、本文、トークンは含まない。

## データモデル（`supabase/migrations/20261122084915_cloud_saves.sql`）

`public.cloud_saves`: ユーザーごとに 1 行。

| 列 | 内容 |
| --- | --- |
| `user_id` | 主キー。`auth.users` を参照（ユーザー削除でセーブも消える）。既定値は `auth.uid()`。クライアントは指定できない |
| `data` | `jsonb`。オブジェクトで、2 MiB 以下（check 制約） |
| `schema_version` | スナップショットの形式のバージョン（1 以上） |
| `revision` | サーバーが採番する。初回は 1、更新のたびに +1 |
| `created_at` / `updated_at` | サーバーが設定する |

- RLS 有効。ポリシーは `user_id = (select auth.uid())`（SELECT、INSERT の WITH CHECK、UPDATE の USING と WITH CHECK）。
- 権限（#185 の方針どおり、既定では何も付かないので明示する）: `authenticated` に `SELECT`、列単位の `INSERT (data, schema_version)` と `UPDATE (data, schema_version)` だけ。`DELETE` は付けない。`anon` には何も付けない。`user_id`、`revision`、`updated_at` はクライアントが書けない（列権限）。
- トリガー `cloud_saves_server_fields` が、`revision`、`created_at`、`updated_at`、所有者をサーバーで決める。クライアントの値はすべて上書きされる。
- 書き込み RPC `public.upsert_cloud_save(p_data jsonb, p_schema_version integer)`: `SECURITY INVOKER`（RLS と列権限がそのまま効く）。`auth.uid()` が null なら `28000` で失敗する。`INSERT ... ON CONFLICT (user_id) DO UPDATE` で、`(revision, updated_at)` を返す。`EXECUTE` は `authenticated` にだけ付与し、`PUBLIC` と `anon` からは外してある。
- セーブの削除機能はない（このチケットの範囲外）。

## 競合ポリシー

**最後にサーバーが受け付けた書き込みが勝つ。** 端末の時計は使わない。同じ行への書き込みは行ロックで直列化され、`revision` が単調に増える。端末は 2 つの値を持つ。

- `ackRevision`: この端末が最後にアップロード、または復元したときの `revision`。
- `dirty`: クラウドにまだ届いていないローカルの変更がある。

マージはしない。別の端末の変更を知らずにアップロードすると、その変更は上書きされる。ただし、ログイン時の照合（次節）で、未送信の変更がなく、クラウドの `revision` が `ackRevision` より大きければ、先にクラウドの内容を取り込む。

## 同期の対象

スキーマ（`src/js/app/common/context/schema.js`）で `cloudSave: true` を付けたフィールドだけ。旧 `syncToBackend` のメタデータは削除した。

- 含める: `hasSeenCinematic`、`completedObjectives`、`questStatus`、`customAvatar`、`inventory`、`levelState`、`loadout`、`migrations`、`settings`、`teams`、`operations`、`unlockCodes`、`xp`。
- 含めない:
  - `env`（環境変数。秘密情報を含みうる）
  - `extensions`（この端末のディレクトリのパス）
  - `user`（ローカルの GUID）
  - `liveEvent`、音声関連のキー
  - QuestIDE のコードファイル、IndexedDB
- `migrations` から、端末ごとのフラグ `2020-09-16_analytics_id_to_user_guid` を除く。復元時は、ローカルとクラウドのフラグを「どちらかが完了なら完了」でマージする。
- 受信したスナップショットは、`setContext` と同じ Yup の検証にかける。1 つでも不正なら復元しない。`schema_version` がクライアントの `CLOUD_SAVE_SCHEMA_VERSION`（現在 1）より新しいときは、同期を止めて「アプリを更新してください」と表示する。ローカルには触れない。
- 「進行あり」の判定（`hasMeaningfulProgress`）: 完了した目標がある、`xp > 0`、`questStatus` か `levelState` が空でない、初期装備（`tshirt`、`jeans`）以外のアイテムがある。名前、GUID、キーの有無は見ない。

## ログイン時の照合（アカウントごとに 1 回）

同期の状態（`config.json` の別キー `cloudSync`。スキーマ外で、アップロードされない）:

| 項目 | 内容 |
| --- | --- |
| `boundAccount` | このローカルセーブが同期しているアカウントの `account` ハッシュ（なければ `null`） |
| `ackRevision`、`dirty` | 上記 |
| `restoreInProgress` | 復元の書き込み中のマーカー（`{ account, revision }`）。再起動後に復元をやり直す |

ログイン（または起動時のセッション復元）で、クラウドのセーブを取得してから決める。

| 状況 | 動作 |
| --- | --- |
| 復元のマーカーがこのアカウントのもの | クラウドから復元をやり直す |
| 紐付け済みの同じアカウントで、`dirty` | アップロード（最後に受け付けた書き込みが勝つ） |
| 同じアカウントで、`dirty` でなく、クラウドの `revision > ackRevision` | クラウドを取り込む（別端末の更新） |
| 同じアカウントで、どちらでもない | 何もしない |
| 紐付けなし、クラウドになし | アップロードして紐付ける（新しいローカルセーブ） |
| 紐付けなし、ローカルに進行なし、クラウドにあり | 自動で復元（別端末での引き継ぎ） |
| ローカルに進行あり、クラウドにあり | 選択ダイアログ（クラウドを使う / この端末のセーブを使う / キャンセルしてログアウト）。両方の XP と完了目標数、クラウドの最終保存日時を表示する |
| 別アカウントに紐付いたローカルで、クラウドになし | 確認ダイアログ。キャンセルならアップロードせずログアウト |

- キャンセル、ダイアログ表示中のログアウト、アカウント切替では、ローカルにもクラウドにも書き込まない。
- マーカーが別アカウントのもの、またはクラウドのセーブがもうないときは、ローカルは「誰のものでもない」半端なコピーとして、紐付けなしと同じに扱う（選択を求める）。

## 安全な復元

`setContext` でライブに置き換えず、次の順で行う（`common/cloudSave/syncEngine.js`、`common/context/index.js` の `applySavedFields`）。

1. マーカー `restoreInProgress` を保存する。
2. 永続化を抑止し、キューにある保存を待つ。
3. 対象フィールドを store に 1 件ずつ `await` で書き込む。クラウドにないフィールドは削除して既定値に戻す。1 件でも失敗したら、そこで止める。
4. すべて成功したら、`boundAccount`、`ackRevision`、`dirty = false` を保存し、マーカーを消して、ウィンドウを再読み込みする（起動時のマイグレーションとゲームオブジェクトが、復元後のデータで初期化される）。
5. 失敗したら、マーカーを残してエラーを表示し、永続化の抑止を解除する。次回のログインで復元をやり直す。それまで、半端なデータをクラウドへアップロードしない。

`flushPendingSaves()` の完了は成功の証拠にしない（失敗した保存があっても解決するため）。

## 通信失敗、再試行、古い応答

- ローカルの保存は、同期とは独立している。同期の失敗でローカル保存を止めない。
- ローカルの変更は、まず `dirty = true` を保存し、2 秒のデバウンスのあとでアップロードする。アップロード中に変更があれば、`dirty` を残したまま再アップロードする。
- `offline`、`server`、`unauthorized` は、5 秒から始まる指数バックオフ（最大 5 分）で再試行する。ウィンドウの `online` イベント、認証状態がオフラインから復帰したときは、すぐ再試行する。サーバーが拒否した場合（`rejected`、`too_large`）は自動では再試行せず、次の変更で再び試す。
- ログイン、ログアウト、アカウント切替のたびに「世代」を進める。取得、アップロード、選択ダイアログの結果は、開始時の世代と一致しなければ捨てる（Rust 側の `account_changed` と二重の保護）。
- ログアウトでは、予約と再試行を止め、ローカルのセーブと同期の状態（`boundAccount`、`dirty`）は残す。同じアカウントでもう一度ログインすれば、未送信の変更をアップロードする。別のアカウントでログインしたときは、上の表のとおり、無断でアップロードせず確認する。
- 状態は Settings > アカウントに「クラウドセーブ: …」と表示する（同期済み、同期中、オフライン、エラー、選択待ち、要アプリ更新）。

## 「データを消去」との関係

まず同期を止める（書き込み中の復元は先に終わり、その後は何も書かない）。ローカルのデータを消したあと、`cloudSync` を消し、ログアウトする（セッションが残ると、空のセーブがすぐクラウドの内容で復元されてしまうため）。どちらかを確認できなければ、エラーを表示して再起動しない。クラウドのセーブは消えない。もう一度ログインすると、空のローカルとして扱われ、クラウドのセーブが自動で復元される。

## ランキング、チームスコアとの関係

`xp` と `completedObjectives` は、クラウドセーブに**保存・同期される**。ただし、自己申告のデータなので、ランキングやチームスコアには**使わない**（先頭の信頼境界を参照）。設定画面の説明（`settings.teamsDescription`、`settings.operationsDescription`）にも、保存されることと、順位には使われないことを分けて書いてある。

Firebase の `user-sync` を削除したため、旧 API への送信はなくなった。チームとオペレーションの参加コードの検索、参加、離脱の処理、Firestore のライブイベント（`liveEventAchievements`）、解除コード（`unlockCodes`）は、このチケットでは変更していない。

## 検証

| 内容 | コマンド |
| --- | --- |
| DB（RLS、権限、revision、所有者、匿名の拒否） | `npm run supabase:test`（`supabase/tests/database/cloud_saves.test.sql`） |
| JS の単体テスト（スナップショット、照合、復元、再試行、古い応答、選択ダイアログ） | `npm test` |
| Rust の単体テスト | `cargo test`（`src-tauri/`） |
| ローカル Supabase に対する統合テスト | 下記 |

統合テスト（`src-tauri/tests/cloud_save_local_supabase.rs`）は、使い捨てのユーザー 2 人をローカルの管理 API で作り、パスワードでサインインしたセッションを、実際の `AuthManager` と `CloudSave` に渡す。端末ごとに別のセッションを使う。OAuth の往復ではない。確認する内容は次のとおり。

- 新しいローカルセーブのアップロード（クラウドになし → revision 1）
- 既存のクラウドセーブの上書き（revision が増える）
- 別の端末が同じセーブを読める。2 つの端末が交互に書くと、最後に受け付けた書き込みが残る
- 接続できない（接続先を到達不能にする）と `offline` で失敗し、クラウドの内容は変わらない
- 別のユーザーは、他人の行を読めず、更新も削除もできず、`user_id` を偽って挿入もできない。ログインなし（publishable キーのみ）では何もできない。`expectedAccount` が違う呼び出しは、リクエストを送る前に拒否される

選択ダイアログ、自動復元、通信断でもローカル保存が続く点は、ログイン時の照合の判断を含めて、JS の単体テスト（`src/test/app/common/cloudSave/syncEngine.test.js`）で確認している。

```bash
npm run supabase:start
eval "$(npx supabase status -o env | grep -E '^(API_URL|PUBLISHABLE_KEY|SERVICE_ROLE_KEY)=')"
TERMINALQUEST_TEST_SUPABASE_URL="$API_URL" \
TERMINALQUEST_TEST_SUPABASE_PUBLISHABLE_KEY="$PUBLISHABLE_KEY" \
TERMINALQUEST_TEST_SUPABASE_SERVICE_ROLE_KEY="$SERVICE_ROLE_KEY" \

```

## 手動確認（実際のアプリ）

OAuth の資格情報（[auth.md](auth.md)）が必要で、自動テストでは確認していない。

1. 端末 A で進行したローカルセーブを作り、ログインする。クラウドになければ、アップロードされ「同期済み」になる。
2. 端末 B（または「データを消去」したあと）で同じアカウントにログインする。空のローカルなら自動で復元され、再読み込みされる。進行のあるローカルなら選択ダイアログが出る。
3. ネットワークを切ってプレイし、再接続して同期されることを確認する。
4. ログアウトして別のアカウントでログインし、無断でアップロードされず確認が出ることを確認する。
